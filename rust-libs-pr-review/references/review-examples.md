# Observed review techniques

These examples connect review techniques to substantive discussion and inline comments on `rust-lang/rust` PRs, inspected on 2026-09-05. They illustrate techniques and context-specific judgments. Use them as historical evidence, checking the current code and discussion before applying a precedent.

## Semantics and tests

- **Verify semantics using independent operations.** On [#153239, `Ancestors` double-ended iteration](https://github.com/rust-lang/rust/pull/153239#discussion_r2970445163), the review compared forward iteration, reversed backward iteration, and repeated `parent()`, while explicitly bounding platform coverage. Later discussion argued that [tests could not compensate for difficult-to-review duplicated path logic](https://github.com/rust-lang/rust/pull/153239#issuecomment-4322177474), and preferred reusing `Components` while identifying the remaining boundary assumption. Transfer: demand an explainable invariant as well as informative tests.
- **Make examples distinguish semantics.** On [#147696, integer bit methods](https://github.com/rust-lang/rust/pull/147696#discussion_r2488692563), a non-palindromic bit pattern would teach which end index zero means. The review also [checked the accepted overflow-check behavior against actual behavior](https://github.com/rust-lang/rust/pull/147696#discussion_r2488704661). Transfer: examples and tests should discriminate between plausible interpretations, including build-mode behavior.
- **Test the additional property, then calibrate its value.** On [#161209, `next_power_of_two`](https://github.com/rust-lang/rust/pull/161209#issuecomment-5365167129), the review requested a check for the relation to the input; [later discussion](https://github.com/rust-lang/rust/pull/161209#issuecomment-5486990527) treated its uncertain optimization benefit as nonessential. Transfer: ask for a discriminating check without turning every plausible optimization into a permanent landing condition.

## Performance and maintainability

- **Demand the right performance evidence and explain the trick.** On [#161019, decimal parsing](https://github.com/rust-lang/rust/pull/161019#issuecomment-5470798081), the review requested measurements across the relevant integer-parsing benchmarks and a description centered on motivation. The [inline review](https://github.com/rust-lang/rust/pull/161019#discussion_r3890340076) asked why the constants make the algorithm work, rather than accepting “SWAR” as an explanation. Transfer: cover the cost distribution and the reasoning a maintainer must preserve.
- **Benchmark the experience being changed.** On [#156496, `Components` optimization](https://github.com/rust-lang/rust/pull/156496#issuecomment-4615192376), the review distinguished path-heavy Cargo runtime from compiler-oriented performance measurements and asked about Windows coverage. The discussion [clarified that prospective public path types were a separate API discussion](https://github.com/rust-lang/rust/pull/156496#issuecomment-4615642123), and later [identified the mismatch between a debug-profile question and a release-built std](https://github.com/rust-lang/rust/pull/156496#issuecomment-5466710533). Transfer: benchmark configuration is part of the claim, and future design discussion need not engulf the present implementation review. The early preference for no regressions on this PR is not a universal ban on performance tradeoffs.

## Platform contracts

- **Trace initialization through platforms.** On [#160219, `Thread::os_id`](https://github.com/rust-lang/rust/pull/160219#discussion_r3741732311), the review followed native-thread initialization into the SGX implementation and involved its maintainers. The discussion also [questioned the use case for a weak uniqueness promise](https://github.com/rust-lang/rust/pull/160219#discussion_r3741699838). Transfer: follow shared helpers across lifecycle boundaries and make guarantees no stronger than justified.
- **Check the native contract and preserve failure rationale.** On [#161951, Windows `canonicalize` fallback](https://github.com/rust-lang/rust/pull/161951#discussion_r3884980939), the review requested an explanation of when the ordinary path fails and why the fallback succeeds. Another [comment checked a return-value assumption against Microsoft's documentation](https://github.com/rust-lang/rust/pull/161951#discussion_r3884996138). Transfer: a working-looking fallback still needs a reason and the right native error semantics.
- **Calibrate platform semantics and performance tradeoffs.** On [#160219](https://github.com/rust-lang/rust/pull/160219#discussion_r3926273614), the review treated SGX identity wording as a nonblocking documentation concern; a separate comment [raised post-fork cache behavior](https://github.com/rust-lang/rust/pull/160219#discussion_r3926316938), with a [summary acknowledging the potential performance tradeoff](https://github.com/rust-lang/rust/pull/160219#pullrequestreview-5104041081). Transfer: keep limitations, defects and decisions distinct rather than assigning every caveat the same severity.
- **Resolve today's target question without requiring tomorrow's refactor.** On [#152084, QuRT support](https://github.com/rust-lang/rust/pull/152084#discussion_r3235900678), the review asked for consistent Unix classification across the diff. The [meeting follow-up](https://github.com/rust-lang/rust/pull/152084#issuecomment-4443228591) communicated the conclusion for that target and deferred a broader definition to separate work. Transfer: check shared `cfg` effects and distinguish the decision needed now from desirable architectural cleanup.

## API scope and compatibility

- **API similarity is not identical approval, but deviations need judgment.** On [#161577, byte-slice `split_ascii_whitespace`](https://github.com/rust-lang/rust/pull/161577#discussion_r3878133591), the review noted that `remainder` exceeded the originating ACP, considered it acceptable, and requested an explicit dependency on the separate string-remainder issue given the gating limitation. The [implementation review](https://github.com/rust-lang/rust/pull/161577#pullrequestreview-5048161869) asked for non-ASCII and terminal-whitespace cases. Transfer: surface the dependency accurately; do not convert “outside the ACP” into an automatic rejection or assume factored code needs no tests.
- **Nightly additions can affect stable users.** On [#141994, `Iterator::contains`](https://github.com/rust-lang/rust/pull/141994#issuecomment-2980947079), the review traced an unstable addition to warnings for existing Itertools users, then [narrowed the needed prerequisite to preventing the collision warning](https://github.com/rust-lang/rust/pull/141994#issuecomment-2980949300). Transfer: trace actual downstream effects and distinguish the fix needed to experiment from the conditions for eventual stabilization.
- **Inspect what an API makes externally observable.** On [#106418, ordering `Discriminant`](https://github.com/rust-lang/rust/pull/106418#pullrequestreview-1594299402), the review analyzed how exposing order could constrain library authors' future enum changes. The review also [checked a claimed codegen disadvantage against a concrete alternative](https://github.com/rust-lang/rust/pull/106418#issuecomment-1698596424). Transfer: consider downstream maintenance freedom and test claims about alternatives.

## Review conclusions

- **Make conditional approval legible.** On [#159805, native-path conversion](https://github.com/rust-lang/rust/pull/159805#issuecomment-5231926773), the review explained the limited remaining condition behind `r=me`. On [#153239](https://github.com/rust-lang/rust/pull/153239#pullrequestreview-4343992122), the review requested a description of the final implementation. Transfer: say exactly what remains, and do not make the next reviewer reconstruct an abandoned design.
- **Clearly separate nits from conditions.** In [#161951's final discussion](https://github.com/rust-lang/rust/pull/161951#issuecomment-5503010138), the final review explicitly said the remaining suggestions did not block merging. Transfer: optional readability preferences should remain optional; the number of comments is not the seriousness of the review.

## Research limits

The sample intentionally favors substantive, informative reviews across platform code, API changes, iterators, documentation and optimization. It is not an exhaustive survey or evidence that every suggestion was correct. Reviewing discussion to extract technique does not re-review the underlying patch or establish that its tests pass today. Generic advice was retained only where it changes a review decision; specialized soundness methodology stays in the dedicated stdlib skills.
